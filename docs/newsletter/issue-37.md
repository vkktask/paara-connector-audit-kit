## 1. The Connector Pattern — the personal file store, reached from a second AI side

This week's pattern to check in your own estate:

Teardown #23 tested OneDrive → Microsoft 365 Copilot. Teardown #44 tests **OneDrive → ChatGPT**: the same personal file store, reached from a different AI assistant, from outside the tenant the files live in. Together the two teardowns complete the OneDrive pair — and the pair is the pattern. The store does not change, the route does, and the route is where the risk lives. A second AI side means a second grant over the same files, a second approval surface, and a second log story.

- The read reach is the drive as the account actually holds it. A personal OneDrive rarely holds only its owner's own work. It holds years of drafts, contracts, board packs and HR letters — plus everything colleagues ever shared into it, which arrived carrying their owners' sharing settings. Tested in Teardown #44 on a **test tenant with dummy files only**: the connecting user's own files folder by folder, a **shared-with-me set** shared in by a second account the user was never pointed at, and a **control file** never shared with the connecting user at all. The filmed question is whether the reach is the one file in the conversation, or every file the account can open.
- The write reach is wider than the summarising story that sold it. Upload, edit, share, delete — and the write this teardown adds to the file series: **create a sharing link**, a grant nobody filed, minted at conversational speed on whatever defaults the platform chose. Where the user can widen an existing file's audience, the write reach also includes turning a one-colleague share into an anyone-with-the-link share. Each write is filmed in Teardown #44 with the approval step, or its absence, on camera.
- There is no dataset shortcut for this one. OneDrive → ChatGPT is **not** one of the 13 connectors in the published documentation audit, so no documentation score, factor code or band carries over — and nothing carries over from Teardown #23 either, which tested the same file store from a different AI side. Teardown #44's scorecard is blank until the film.

That is a pattern, not a finding about a named product. No vendor score is published here, and Teardown #44 is not filmed yet — its scores are blank until the film. Check the pattern in your own estate first — the fix is in Section 5.

## 2. Field Note — The Personal Drive at Work

Issue #23 made the account argument: the connector review asks which tool and which scopes, but the question that decides everything else is whose account sits behind the grant — a managed work account the organisation can audit, restrict and revoke, or a personal account it cannot even see. That argument was about identity. This one is about the quieter mechanism underneath it, the one that moves the files themselves: **sync**.

Sync is sold as convenience, and it is genuinely convenient. The personal OneDrive or Drive folder appears on the work laptop, so the photos, the personal documents, the side-project files are just there. The work folders sync out to the personal cloud, so the deck is reachable from home, from the phone, from the tablet. Nobody decided any of this as a data policy. It arrived as a default, one helpful prompt at a time — "back up your folders?" — and it has been running ever since, in both directions, on most machines in the estate.

Follow what sync does to the boundary the rest of your governance assumes. A file that started personal now sits inside the work machine's file system, inside the work backup, inside the work endpoint agent's view — and, the moment anyone connects an AI tool to that machine's files or to the work account, inside the connector's reach, classified by nobody as anything. A file that started as work — the contract draft, the customer list, the board pack — now sits in a personal cloud, under consumer terms, outside the tenant's audit log, outside retention, outside the leaver process. When that person leaves, IT disables the work account on the last day. The synced copies in the personal cloud do not get the memo. Issue #16's leaver's token was about grants that outlive the account; the synced folder is the same failure in file form — copies that outlive the employment.

Now add the agent, because the agent is why this matters this year and not five years ago. A connector does not know which side of the line a file came from. It reads the folder in front of it. Connect an AI assistant to a work account whose drive includes a synced personal folder, and the assistant's reach includes the personal folder — tax returns, family documents, a solicitor's letter — summarised into a work conversation, logged (if anywhere) as work activity, under a work identity. Connect a personal AI subscription to a home machine whose folders include synced work files, and the work data is being processed under consumer terms by a tool the organisation has never heard of — Issue #23's shadow AI, except the staff member may honestly believe they did nothing wrong: they connected their own tool to their own files, and sync had already decided the files were theirs. The person is not the failure here. The blur is.

Teardown #44 tests the governed version of this pattern — OneDrive → ChatGPT on a managed test tenant, dummy files only, with a control file that must stay out of reach. It is not filmed yet, and this note claims no result from it. The personal-drive version needs no film: open one work machine in your own estate — with its owner's permission, in the room — and list what is syncing, in which direction, from which account. Then ask which connectors can reach each folder. The answers are the finding, and they are already available to you.

The lesson for leaders: sync is a data-flow decision that was never taken as one. It moves personal data into work reach and work data into personal custody, continuously, by default — and every connector grant you approve inherits the result. Section 3 gives the rules that draw the line back — not by banning sync, but by deciding it.

## 3. Harness — Sync and personal-cloud rules for agents

Issue #23's harness section built the inventory: five places to look, reconciled and keyed by data source. This section is the rule set that inventory feeds — the sync decisions to write down before the next connector approval, because a connector approved against a blurred store is approved against a store that does not match its paperwork.

**Rule 1 — What may sync is a written list, not a default.** For each population of machines, the approval record names: which folders may sync to which cloud, in which direction, under which account — work cloud to work machines under the work account; personal cloud to work machines: not at all, or named folders only, with the owner told in writing what that means. "Whatever the setup wizard suggested" is not a sync policy. The list is short on purpose: if a folder class cannot be named, it does not sync. This is the same discipline as Issue #33's classification applied one layer down — the class decides, and the class is set by decision, not by a backup prompt.

**Rule 2 — The agent inherits whatever sync made adjacent; price the grant against the synced store, not the tidy one.** When a connector is approved over an account or a machine, its real reach is the union of the store as designed and the store as sync has rearranged it: the personal folder that syncs into the work drive is inside a work connector's reach; the work folder that syncs out to a personal cloud is inside whatever that person later connects at home. The rule: the connector approval's reach statement is written against the synced reality — the inventory from Issue #23, plus the sync list from Rule 1 — and any sync path that would put a data class inside the grant that the approval would not accept directly is closed first, or written into the approval as accepted risk with a named owner. An approval that describes the store you wish you had is Issue #6's paper vs production, at the file layer.

**Rule 3 — Unsyncing is an offboarding step, on the same checklist as the token.** Issue #16's revoke list ends the leaver's grants: disable the identity, revoke the tokens, kill the sessions, transfer ownership. Add the file line: on the last day, the sync relationships end too — work folders stop syncing to personal clouds, the personal copies of work data are called back or deleted under the leaver process your counsel has approved, and the check is evidenced, not assumed. The honest limit belongs in the record: an organisation cannot reach into a personal account and delete at will, which is exactly why Rule 1 exists — the time to keep work data out of personal custody is before it syncs, not after the resignation letter. Offboarding can close the pipe; it cannot unpour what already flowed. Price that asymmetry into the sync list.

**Rule 4 — A sync change is a connector change.** Issue #13's re-approval triggers were scope change, tool-definition change, vendor change, new data class. Sync manufactures the fourth one silently: a new folder added to sync, a new device enrolled, a personal account signed in on a work machine — each can move a new data class inside an existing connector's reach without the connector changing at all. The rule: the events that change what syncs are listed in the approval record as re-review triggers for every connector over that store, the way Issue #36 lists mailbox access changes as triggers for the mail approval. The grant did not change. What the grant can reach did. That is the same event, for risk purposes.

**The agent-specific line.** None of these rules is a setting on any connector. They live in the device policy, the sync configuration and the approval record — which is precisely why they get missed: the connector review looked at scopes, and the sync decisions were taken by a setup wizard. Price the file grant against the estate as sync has actually arranged it, the way Issue #34 prices a grant against the tenant as it actually stands.

## 4. Regulator / Industry-Body Update — NIST AI RMF Playbook: a standing feedback route, open and rolling

This week's update is a route, reported at exactly that status — an open door, not a submission. This section claimed a version of it once before, in Issue #18, and it is worth restating because the door is still open and still the lowest-friction way for a practitioner to put connector-layer evidence in front of the body that maintains the AI Risk Management Framework's companion guidance.

**The NIST AI RMF Playbook — the companion playbook to the NIST AI Risk Management Framework — takes feedback on a rolling basis, by email, with no deadline.** That is the whole fact, and it is stated at the precision the industry-bodies scan of 16 November 2026 verified: virtual, by email, rolling, no closing date. Practitioner feedback on the Playbook's profiles, practices and suggested actions is the input NIST says it uses to keep the Playbook a living document rather than a fixed publication.

**No submission is claimed here.** Nothing in this issue should be read as "we filed Playbook feedback" — we have not, in this newsletter's record, and the distinction is the standing rule of this section: submissions are reported as submitted, inquiries as inquiries, and open routes as open routes. If feedback is sent, it will be reported here as a new fact with a date on it, the way the NIST comment filings in Issues #7 and #9 were reported when they were actually sent.

Why this route, for this readership? Because the Playbook is where AI RMF language becomes the practices auditors and governance teams actually run, and the connector layer — grants over existing stores, agent identity, reconstructability — is exactly the kind of operational gap that playbook feedback exists to surface. A short, evidence-led note from a practitioner who has run the audits — what the govern/map/measure/manage functions look like when the system under governance is an agent holding delegated access to the mailbox, the drive and the CRM — is the contribution this route is built to receive. The kit, the dataset and the method behind it are open source, so anything sent can point at evidence a reviewer can check rather than claims they have to take on trust.

## 5. The Monday Fix — map one person's sync, both directions

Forty-five minutes, this Monday — one volunteer, their work machine, and the sync list nobody has ever written down:

1. Pick **one person whose account already carries an AI connector** — a volunteer, in the room, screen shared with them present. From the machine's own sync clients, not from memory, list: every folder syncing, in which direction, to which cloud, under which account — work cloud under the work account, personal cloud under a personal account, anything else found. Record the list with a date on it — Issue #25's rule: evidence or it didn't happen.
2. **Mark the crossings.** For each folder, one of three marks: work data in work custody (expected), personal data inside work reach (a privacy decision nobody took), work data in personal custody (a custody decision nobody took). Count the crossings; do not fix anything yet. The count, on one page, is the artefact this fix exists to produce.
3. **Write the dispositions:** for every crossing, either close the sync path (unsync the folder, move the data to its proper side, confirm the copy state afterwards) or record it as accepted risk in the connector approval for that account, with a named owner and an expiry — Rule 2's discipline, applied to one real machine. Add the leaver line to the same page: what ends, sync-wise, on this person's last day (Rule 3).
4. **File the page** — the sync list, the crossings, the dispositions — with the account's connector approval, and set the trigger from Rule 4: any change to what syncs on this machine re-opens the approval. Then book the same forty-five minutes for the next volunteer. One machine a week is slow, and it is also how the estate's real sync map actually gets drawn.

Score the connector before you trust it — and draw the sync line before the agent inherits it, because a connector reads the folder in front of it, and sync decided which folder that is long before the approval meeting. This Monday, one machine's map is the fix.
